> **课程来源**：FDE 实战训练营第一期 · 第 13 节
> **时长**：约 1 小时 15 分
> **核心问题**：还是 Agent + 知识库 + Skill，凭什么从几千块走到一万元？

本节目录：卖给谁 → 产品表与 SKU → 飞书高级权限 → 客户档案 → 家规文件 → 销售三块 → 数据分层 → 作业。

昨天是电商参考图 / 门店素材 → 小红书帖，千元档。课上演示用的是上个月 demo，并不完善，时间也紧——这本身也是实话：万元档卖的是结构和权限，不是完美产品。

> 至于怎么样生成这些好看的帖子，那就是我们的商业机密了，这个确实不能告诉大家。反正就是知道 OK 有这么一个事情就可以了。

思路还是把 Agent + 知识库 + Skill 封装成更好用的东西。真要落到每个字段和客户习惯，细节非常多，往往要打磨不止一个月、可能两三个月。这节只走基本流程和解法。走完原理就可以上手手搓一版表和权限；落地细节要和客户磨。

## 一、和昨天的差别：事可以一样，人和问题不一样

从千元到万元，老师认为至少三条：

1. **销售能力**。同一套东西，有人卖 5000，有人卖 1 万。靠三块：拿得出手的案例、让人觉得能解决问题的方案、口才。
2. **卖给谁**。中小公司同一套小红书工作流，可能只有几千到一两万；上市公司同一套，可以卖到 5～10 万——问题更贵，价格才上得去。
3. **问题有多大**。昨天替代的是「小红书运营」这一个岗位；若是一整个自媒体团队、一个部门，方案就是部门级，基本上到万元水平。

> 千元档和万元档，其实你干的是一样的事情，只不过你卖给了不一样的人。

要稳定收到万元，优先选**业务部门的核心痛点**，而不是再做一个聊天框。三个入口：

| 入口 | 客户真正问的 | 你要落的东西 |
| --- | --- | --- |
| 产品 | 我卖的是什么、怎么用 AI 管起来 | 产品知识库、SKU 管理 |
| 客户 | 谁来买单、关系怎么接得住 | 客户档案、偏 CRM 的表、方案辅助 |
| 销售 | 怎么卖出去、怎么持续卖 | 获客内容工厂、售前助手、售后 AI 客服 |

产品要回答「卖什么、解决什么」；客户要回答「谁来找你买单」；销售拆成获客、售前、售后。阿里那边老师讲过他们在推的销售助手类 SaaS（课上称 Okki），是售前板块的一种市面解法；售后 AI 客服已经有很多成熟做法。

先把昨天的流程当「加法」的底。千元档：问诊（替代小红书运营、预算几千）→ 图和文案库 + 飞书评论做数据标注 → 生图 Skill、营销文案 Skill、发布 Skill → 统领 Skill 调用三个 → 几乎全自动制作发布。万元档干的是同一套方法，只是岗位从 1 个变成好几个：产品一套、客户一套、销售一套。

## 二、产品知识库：先是一张表，不是一个智能体

万元档仍是加法：千元档解决一个岗位，万元档用同样方法做好几套。**单是产品这一套**，看复杂度就能卖 1 万往上。制造业、只要接触过带 SKU 的公司，仓库里「1 万张升降桌、编号 T001、尺寸材质颜色」这类账，几乎一定有。你要搭的就是这本账，再加填写 Skill。

产品知识库首先应是**表格形态**。飞书多维表格里，第一列老师几乎总会放**编号**。示例字段（课上用升降桌脱敏）：

- 产品编号：如 `T0001`（字母 + 数字）
- 产品名称、规格、尺寸（有单位就带单位，或写成「50×70×120」这类文本）、材质、颜色
- 库存数量（整数）
- 物流编号、物流进度（单选：未发货 / 已揽收 / 已发出 / 已送到站 / 已接收等，按客户实际改）
- 物流负责人（人员字段）

每个产品还该有哪些列，**case by case**，看具体客户。课上随手填的演示行：名称升降桌、尺寸 50×70×120、颜色桃木色、材质封木、库存 1 万——只为说明「基本信息长什么样」，不是标准数据模型。

梳理清楚后，多维表格可以在一定程度上替代 SKU 管理。下一步几乎每张表都能复用：把表头示例发给模型，「拆解分析表头有哪些信息、什么格式，做一套填写这张多维表格的 Skill；这里有大量以前的 Excel，按这套 Skill 填进去。」数据一大，人不可能手工一行行录。产品更新，本质是更新这张库里的内容。

物流若公司已有 ERP，往往有物流接口，接过来让表自己更新。课上演示的是飞书里顺丰轨迹类捷径：引用物流编号 + 客户手机号，用第三方 API key 关联（大约几十块、最多约 50 块，查询上万次量级）。识别出快递公司、单号、官网、揽收 / 签收时间、城市节点等。接口细节因客户内部系统而异，笔记只保留这条路。

## 三、权限：万元档看起来像「管理系统」的原因

产品库通常只有产品部门用；查询可以指定一个人或开一个接口。要做细，用飞书多维表格**高级权限**：

- 角色：超级管理员、普通用户、实习生（名称按客户改）
- 数据表：可管理 / 可编辑 / 仅阅读
- **字段权限**：普通用户可以看不见物流进度、客户手机号、负责人；实习生可能连物流编号都不可读
- 所有者、管理员、编辑者、阅读者是内置档；自定义角色再「添加成员」

开启高级权限后，才能按协作者做精细配置。飞书机器人若以用户身份查看，就按该用户的 User ID 走权限。

数据量大了，多维表格**会慢**。两万行可以扩容；理论上能到约 100 万行，要更高级的飞书 SaaS。

解法不是换神话数据库，而是**拆子表**：产品基本信息一张、产品物流信息一张，用同一产品编号对齐。老师也提到双向关联一类能力，让两表对上。查询时精确打到子表，减少重叠。

行数能堆上去，上下文却堆不进去。设计表结构要像 RAG 切块：分层、命名带编号（如 `A01 客户档案`），让模型去找表，而不是把 100 万行塞进窗口。

> 几万块的，你也不可能给他手搓一个 ERP 系统。也没有必要……简单管用。

## 四、客户档案：编号、文档、表格穿插

再建一张客户表（课上演示名按 CRM 来理解）。小型、中型公司内部往往没梳过完整 SOP / SKU / CRM，你来梳的时候同样**第一列给编号**。

为什么必须有编号：第二行客户姓名叫梁文峰，后面 `C008` 也可能叫梁文峰——到底是哪一个？`A001` 和 `C008` 才能分开。基础列还可以有：年龄等基本信息、手机号、购买产品（多选，可能同时买升降桌和人体工学椅）、订单编号。

**客户档案**用超链接指向飞书云文档，例如 `A001-梁文峰`。文档里再挂：

- 微信聊天记录（按日期做三级标题；当时 WeChat client 不好用，老师说回头再推荐）
- 给过的方案（继续超链）
- 录音和飞书妙记：智能纪要、原文，按日期（如 2026-08-14）

表格管索引，文档管上下文，两类数据穿插。这就是前面知识库课的 **Wiki link**：档案是总目录，点进去才是昨天的纪要、某一版方案。

一层层可以记成这样（课上说真要全搭出来能讲到第二天中午，只记逻辑）：

```
CRM 表（编号 / 姓名 / 手机 / 产品 / 订单）
  └─ 客户档案 A001
        ├─ 微信聊天记录（按日）
        ├─ 方案一、方案二（超链）
        └─ 2026-08-14 妙记 → 智能纪要 / 原文
```

层层嵌套是为了**不让单次上下文太长**，又能精确找到「8 月 18 日跟这个客户聊了什么」。几万块不要手搓 ERP，这样搭就够用。

评论区问订单编号谁生成：都可能——别的系统（小程序 / 抖店 / 淘宝）、自己编、或表格按规则生成。有接口或能在浏览器抓，就做「先生成编号 → 复制导出 → 回填表格」的 Skill。

飞书好用的地方，一是权限能做到字段和子表，二是有了飞书 CLI，可以把「以后客户信息都记在这些链接和编号里」写进 **Agent.md**。老师自己手头客户就是这么档的：档案文件夹 + 每户一档 + 妙记。团队有技术同学在捣鼓替代微信采集的方案，课上未展开，等群里分享，笔记不编造工具名。

## 五、Agent.md：记忆不可靠时的家规

WorkBuddy 记忆、ChatGPT 记忆，都是有时读有时不读。所以设 `agent.md`（Claude Code 里是 `CLAUDE.md`；Codex 当时还没有标准文件，老师自建 `codex.md` + hook，会话开始强制读取）。家规解决的是**长期必须遵守的规则**，避免失忆。

课上实例：Claude Code 装了飞书 CLI 后，用 **bot 身份**写云文档，写完不给编辑权限，每次拿到的都是只读。写进家规：每次开管理权限。后来改成用自己的 **user id** 创建，人直接拥有全部权限。名字怎么称呼也可以写死——哪天不按家规叫，就说明上下文漂了（现在压缩好一些，不像早期那样动不动丢记忆）。

Wiki link 的用法与第 8 节、数据治理课同一套：原图、说话指南、各客户文档互相串；根目录做总目录。每个客户沟通一份单独文档，档案里只留链接。

## 六、销售三块：还是 AKA，只是库和 Skill 换了

- **获客**：内容工厂。昨天小红书那条，再加上公众号、抖音，三条串起来才叫工厂。
- **售前 / 销售助手**：销售知识库 + 销冠访谈得到的 SOP → 销售 Skill → 加一个对话窗口。对销售理解差，录音丢给 AI 是六七十分；有自己的 knowhow 才能梳清楚。老师给某个客户做的助手是**三栏**：左边实时转写（兼会议纪要），中间实时销售策略 / 树状图（现在谈到哪、怎么说服，流式输出），右边像 WorkBuddy 一样的对话窗。
- **售后**：产品知识库 + 客服知识库 + 客服 SOP / Skill + 接口。检索召回率回到第 9 节 RAG：切片逻辑和策略。

有知识库为什么还要 Skill？库只是上下文；**怎么跟客户谈**要靠 Skill。再加对话窗，等于旁边站着一个助手。

产品这块讲清楚卖点、有案例，大约 **3～5 万**能卖；销售助手做精细，可以到约 **10 万**；客户 + 产品大约也是 3～5 万。ERP 最贵，可能到百万级，这节讲不清，老师说后面再拆。商品维护 + CRM + 售前内容 + 销售 + 售后客服一整套，小公司也看付费能力，课上判断大约 **20 万往上**；同样一套给上市公司，数据量和问题都贵，**百万起**。没有标准答案，回到「找更贵的客户」。

销售助手课上是电脑端。手机当时几乎不能本地部署：一条路是 WorkBuddy 助理 + 微信小程序连本地；另一条是云服务器上的小程序或网站。

## 七、数据加载、旧系统和「先数字化」

飞书扛不扛得住？老师说目前给客户做的，慢一点但可以，能到约 100 万行。真难点是：不能把 100 万行丢进上下文。表要切细、分层，让模型先找到 `A01` 再找 `A001`。单个表他们没做到超过 10 万行；多表加起来小千万级有过。

用户已有分散在各个第三方里的系统，要不要重搭飞书？很复杂。重搭等于再买飞书企业会员，**动辄几十万**。客户不愿买，就先给「大概的解法」：每个软件开 API 或扒数据，统一存本地，或存进某个员工账号下的多维表格。Square 一类也可以，但团队协作、飞书 CLI 成熟度是他们常用飞书的原因。

多维表格可以当成**低代码**：不用自己写数据库，懂业务、带对方把字段梳一遍，再让 AI 填。实时性：有 API 就定时（例如每半小时），Skill 里再加确认或交叉验证。读取靠飞书 client，不必全表遍历，靠目录分层定位。

微信语音转不了文字，当时技术攻防问题，老师说没办法。没有飞书、企微、钉钉，只剩微信 + 老 OA：没有好解法，除非预算够到把整套重做一遍、上 BI / CRM 界面——那就不是 10 万、20 万能解决的。企微智能表格、钉钉多维表格原理差不多。医院、政务很多用钉钉。先进公司用飞书用久了资产都在上面；「让他们下一份飞书」容易，**员工用不用**才难。

「大部分时间都在梳理客户数据」——对，上 AI 之前先数字化。万元卖的就是这摊脏活。客户使用场景你不熟，比如聊天记录怎么录入，也要当场问清楚；语音转写做不到的，当时老师承认没办法。

课上还有几句问答，避免自己发明「更高级」的架构：

- 飞书机器人以用户身份查看，就按 User ID 分配权限——是的。
- 产品数据量大查询会慢——会，所以拆子表、精确查，而不是先上独立数据库。
- 用户已有分散系统，Square 会不会更稳——也可以；他们常用飞书是因为协作和 CLI。
- 整理数据的准确性、实时性：数据治理本身就是复杂话题；有接口就定时抓，Skill 里再交叉验证。
- 阿里会不会出面向 AI 的数据仓库：老师说应该会，细节不知道。
- 老派公司没有飞书，怎么在现有系统里「看见」这些操作：用企微或钉钉同类表；再老就没招，除非预算够到重做界面。

## 八、现场补充：上市公司并不缺 Agent

当天老师在上市公司拜访。深水区的现象：有的总经理 Codex 用得比 IT 还溜；公司自建 Agent，也有 WorkBuddy、Codex。他们自己承认：专门成立 AI 部门去做内部 Agent，**开发不过** WorkBuddy 和 Codex——对面是整厂团队。但 WorkBuddy 找上门也推不动：做得**太重**，很多公司还是五年前的笔记本，一跑任务就卡，有人改在私人电脑偷偷用，公司管控不到。AI 部门 KPI 是在 WorkBuddy / Codex 出现之前定的，做到一半发现落在大厂射程里。DeepSeek Harness 轻，潜力大，但要看生态和企业级稳定性，课上没有下结论。

更新产品库，本质是更新表里的内容。查询可以指定一个人，或给一个接口，不必人人直接改底表。数据权限问「要不要做 Agent 权限管理」：产品库一般只有产品部门用；要细，就上高级权限或拆不同子表。两万行可以扩容；想查得快，把基本信息和物流拆开，编号对齐，必要时用关联字段让两表一起变。

评论区把 iPad 预装同一套工作流、搭配实物去卖，老师说卖到万元没问题——那是销售和封装，不是另一套模型。千元到万元，首先还是销售能力。

## 九、作业

任选一家能拿到公开信息的公司，做**产品知识库**或**客户 CRM** 的表结构（交产品知识库系统即可）。

> 这种万元级的问题……他卖的是这个数据治理，脏活累活。

只要梳出库，后面接口和 Skill 相对好做。难的是上下文和数据。老师很难拿一家真公司的完整案例讲——稍微公开就可能涉及刑事责任——所以只给思路，不给可指认的案例包。第 3 节的四个标准在这里全部适用：可追溯、可理解、可控制、可相信。业务部门要的是自己能改；你要防止改乱。方案里把字段字典和权限矩阵写清楚，比多做两个炫酷 Agent 更值钱。

## 十、这节课里点过的坑

- 第一列没有编号，表里出现两个同名客户，对不上档案
- 产品、物流、客户全堆在一张宽表，查询慢，上下文一次喂爆
- 靠 WorkBuddy / ChatGPT 记忆当制度，家规没写成必读的 Agent.md
- 飞书文档用机器人身份建，协作的人拿不到编辑权
- 客户已有一堆第三方系统，一上来就要对方再买几十万飞书企业版
- 把万元档理解成「再做一个更炫的 Agent」，而不是字段字典 + 权限矩阵 + 数据治理
- 同一套小红书工作流，给中小公司报上市价，或给上市只报几千——人和问题没对齐
- 公开真实客户的完整档案当教材；老师说这里稍微展开就可能涉及刑事责任

## 十一、这节课可以做的事

- [ ] 写清这个客户是「同一个工作流卖给更贵的人」，还是「从单岗位加成部门级」——两种涨价理由不要混
- [ ] 在飞书建产品表：第一列编号，补齐名称 / 规格 / 库存 / 物流进度 / 负责人，并用高级权限做一版「实习生不可见手机号和物流」
- [ ] 再建客户表：编号规则能区分同名；档案文档用 Wiki link 挂方案、妙记、聊天，表格本身保持瘦
- [ ] 写一份 Agent.md：飞书用用户身份创建、必读的编号规则、客户信息写在哪几张表
