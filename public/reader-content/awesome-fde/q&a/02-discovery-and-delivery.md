# 需求诊断与项目交付：从问题到可验收试点

## 第一次和老板沟通，应该先问什么？

**标准答案：**

先理解经营目标和问题，不先推销某个 Agent。可以围绕以下问题展开：

1. 哪个业务结果最需要改善，为什么现在要做？
2. 受影响的流程、岗位和客户分别是谁？目前怎么完成？
3. 一周发生多少次，每次耗时多少，错误或延迟的代价是什么？
4. 现有资料、系统、权限和接口条件如何？谁负责数据？
5. 谁能担任业务负责人、参与试点并确认验收？
6. 有哪些不能触碰的安全、合规和业务连续性要求？

把回答整理为现状流程、问题证据、目标、约束、待验证假设和责任人，再决定是否值得进入付费诊断或试点。

## 怎样挑选第一个 AI 场景？

**标准答案：**

选高频、耗时或返工明显，输入资料可获得，输出可由人判断，失败影响可控制，并且有业务负责人愿意参与的流程。优先从流程中的一个任务或步骤开始，不要一上来改造整个部门。

对候选场景逐项评估业务价值、数据准备度、系统接入难度、权限风险、员工接受度和可测量性。重要业务不代表适合当第一个试点；如果资料混乱、责任不清或错误代价不可控，应先补基础条件或换低风险场景。

## 咨询、培训、定制、陪跑应该怎样组合？

**标准答案：**

按客户成熟度和目标选组合，而不是固定捆绑：

- 目标和流程不清楚：先做诊断和小范围咨询；
- 员工会用但缺少业务流程：培训配合真实任务演练；
- 流程明确但重复操作多：定制知识库、工作流或系统连接；
- 首次试点缺少内部经验：增加陪跑、数据复盘和迭代；
- 方案运行后需要持续更新：约定维护、监控、回归测试和响应方式。

咨询不是只交一份报告，培训也不承诺自动产生业务结果。每一项服务要写清输入、工作内容、交付物、客户配合事项、范围边界和验收方式。

## 一个 FDE 试点的标准交付流程是什么？

**标准答案：**

可以按以下阶段推进，并根据规模调整：

1. **诊断**：访谈流程参与者，确认问题、基线和约束。
2. **定范围**：选定用户、任务、资料、系统和不处理事项。
3. **方案设计**：明确数据流、权限、自动化步骤、Agent 边界和人工复核点。
4. **原型验证**：用代表性真实样本验证价值与主要风险。
5. **试点运行**：小范围并行使用，记录输入、输出、错误、修改和异常。
6. **评估迭代**：对照验收指标修复问题，做回归测试。
7. **推广或收尾**：达到门槛后扩大范围；未达到则调整、暂停或终止，并交接资料和结论。

每阶段约定负责人、决策门槛和交付物。阶段门槛不通过时不要默认进入下一阶段。

## 如何估算投入、报价和项目范围？

**标准答案：**

先拆工作，而不是按“做一个 Agent”报总价。识别流程梳理、数据清洗、知识整理、系统接口、权限、安全测试、用户培训、陪跑和运维等工作量；标出外部依赖、客户配合和不确定事项。

用小范围付费诊断或验证阶段消化高不确定性，给出范围、假设、明确排除项、变更流程和阶段验收。报价要覆盖交付劳动、风险和持续维护，但不应以未经验证的节省金额保证效果。正式商务条款由双方确认。

## 客户要求“先做个 demo 看看”，怎么处理？

**标准答案：**

先问清 demo 要验证哪个业务假设、用什么资料和样例、由谁判断成功，以及演示后是否进入试点。用合成或脱敏数据可验证交互；要验证准确率、权限、流程收益或系统稳定性，则必须用经授权的代表性数据和真实环境约束。

演示明确标注哪些是模拟、哪些未接入、哪些不能用于生产。把 demo 限定为有目标、有时间和验收标准的验证，不要让演示效果被误认为已交付能力。

## 项目中途不断加需求，如何保护交付？

**标准答案：**

记录原定目标和范围，对新增需求评估业务价值、风险、依赖和额外投入；与客户决定替换原范围、拆到后续阶段或走正式变更。变更后同步调整工期、价格、测试和验收口径。

对安全、权限或正确性相关的问题不能简单当成范围外需求搁置；先评估是否需要暂停上线或收窄使用范围。稳定交付比不断堆功能更重要。
