# Q&A 原篇：一次 FDE 项目理解问答

> 销售跟进邮件是用于练习项目分析的场景，不代表已经交付的客户案例或效果数据。以下按原来的提问顺序保留，并整理为问题与标准答案。

## 企业已经有 Codex 和 WorkBuddy，为什么还需要 FDE？

**标准答案：**

工具提供通用 AI 能力，但不会自动理解企业的制度、产品信息、业务流程、员工权限和系统接口。企业买了工具，不等于员工已经会用，也不等于业务结果已经改善。

FDE 的价值是围绕具体业务目标，把工具、知识、数据、权限、流程和员工使用结合起来，并对试点效果负责。交付应是约定范围内可验证的结果，而不只是工具或演示。

## 企业真正遇到的问题是什么？

**标准答案：**

要弄清企业制度、产品信息和操作流程如何安全地提供给 AI；AI 如何与表格、CRM、ERP、飞书或钉钉协作；不同员工如何只访问获准资料；个人有效用法如何成为团队流程；资料和工具变化后由谁维护。

咨询、培训、定制工作流和陪跑都可能是解决手段，但必须先诊断业务流程、数据条件、权限要求和验收目标，不能只列服务名称。

## AKA 怎样帮助组织方案？

**标准答案：**

- **Agent** 负责理解任务、生成内容或调用获准工具。
- **Knowledge / Database** 提供可信知识、规则和业务状态。
- **Automation** 把稳定、可检查的步骤连接成流程。

从业务任务出发决定需要哪一部分。不要为了用 Agent 而加 Agent，也不要把未经确认的资料直接当成知识库内容。

## 怎样把销售经验变成知识库，让 Agent 跟进邮件？

**标准答案：**

先确认销售在哪个步骤耗时、要用哪些客户和产品字段、信息分别在哪里、哪些经验已由业务负责人确认、当前处理时长和错误情况如何。再筛选有效产品资料、经确认的规则和可复用案例，记录来源、适用条件、版本和维护人。

自动化清洗前定义字段、格式、校验、去重和冲突处理规则，并保留处理日志。第一版让 Agent 生成带资料依据的邮件草稿，由销售审核后发送；暂不让 Agent 自主外发，也不允许自行编造价格或承诺。

## 一周后草稿更快了，但销售几乎每封都要大改，怎么办？

**标准答案：**

先暂停扩大试点，把修改原因分类为事实错误、资料缺失、客户条件不匹配、语气格式问题或流程不合适。检查每次任务输入了哪些字段、Agent 实际检索到什么资料、生成了什么草稿，以及销售如何修改。

根据证据定位到资料、检索、字段映射、生成约束或工作流环节，再用同一组代表性问题回归测试。比较处理时间、修改量、事实错误和人工复核成本；持续达标后再扩大，问题解决不了就缩小、换场景或停止。

## Agent 反复写错产品价格，怎么排查？

**标准答案：**

依次检查三层：

1. **资料源**：最新价格是否存在，有无旧版本、客户特价或冲突资料？
2. **检索**：本次邮件实际使用了哪份价格资料、版本和适用条件？
3. **生成**：资料和检索都正确时，Agent 是否仍写错金额、计价单位或客户条件？

保留任务输入、检索片段和出处、草稿、销售修改稿及修改原因。如果找不到可信的最新价格，Agent 应明确说明资料不足并转交销售核实，不能猜报价；对外发送前由销售确认。

## 知识库搭建正确吗，怎么判断？

**标准答案：**

知识库不是把所有文件和聊天记录堆进去。应检查信息是否准确、有效、来源可追溯、权限合规、结构可检索，并有明确的审核与更新责任。用真实业务问题测试检索是否命中、回答是否有依据、遇到缺资料或冲突时是否会拒答，以及不同员工是否只能看到获准内容。

发生错误时，先确认资料源，再确认实际检索片段，最后判断生成是否误用资料。找到根因后修正对应环节并做回归测试，不要预设所有问题都是知识库造成的。

## FDE 项目最终要交付什么？

**标准答案：**

开始前确定业务目标、当前基线、试点范围和验收口径；交付过程中记录流程、输入资料、权限、测试、异常和员工反馈；结束时交付可用方案、操作说明、维护责任和已知限制。

验收应看业务指标，例如处理时长、事实错误、返工量、采用率或人工复核成本，而不是接入了多少工具。客户要能在真实流程中使用，知道错误时如何停止和升级，也明确后续由谁维护。
