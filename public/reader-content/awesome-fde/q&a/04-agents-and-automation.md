# Agent 与自动化：把流程做稳而不是做炫

## 哪些事情用工作流，哪些事情用 Agent？

**标准答案：**

步骤固定、判断规则明确、结果可验证的任务优先用确定性工作流；需要理解非结构化输入、归纳信息或生成草稿的环节可引入 Agent。常见做法是混合：自动化负责确定性的取数、校验、路由和记录，Agent 负责受约束的理解与生成，再把高风险动作交给人确认。

不要为了“Agent 化”把简单脚本改成自主决策。可控性、可观测性和业务价值比自主程度更重要。

## 销售邮件跟进流程如何设计？

**标准答案：**

先限定一个窄场景，例如“销售查看客户资料后生成下一封跟进草稿”。流程可为：取得授权范围内的 CRM 字段和有效产品资料；检查必填信息；检索相关政策或案例；生成带依据的草稿；显示缺失信息和引用；由销售修改确认；经批准后发送并记录结果。

第一版不要让 Agent 自主决定报价、承诺交期或直接批量外发。对于敏感客户、投诉、合同承诺和无法确认的事实，转交销售或主管。上线前用代表性客户、无资料客户、冲突资料和异常字段进行测试。

## 企业系统如何安全地交给 AI 使用？

**标准答案：**

按最小权限逐项授权，区分读取、草拟、写入和对外发送等动作；为每类用户和 Agent 设置身份、范围、凭证保管、审批和撤销机制。先只读，再考虑可撤销的低风险写入；批量操作和外部发送增加明确确认。

优先使用官方 API、企业集成或经过审核的连接方式，确认数据流向、日志、速率限制和故障处理。不要共用个人账号或把密码、密钥放进提示词。接口调用失败、重复提交或权限不足时应停止并报告，不要伪装成功。

## 如何处理 AI 幻觉？

**标准答案：**

幻觉不能仅靠提示词消除。要降低影响，需要权威资料、合适检索、明确字段和约束、答案依据、拒答策略、回归测试和人工复核共同配合。

对每个风险点设计不同控制：事实回答要求引用来源；价格和数量从权威结构化数据读取；缺数据时拒答；外部承诺由负责人审批；生产运行保留输入、检索、输出、修改和异常记录。衡量的是特定任务和数据上的错误表现，不宣称模型永不出错。

## Agent 什么时候可以自动执行，什么时候必须停下来？

**标准答案：**

只有当任务范围明确、资料可信、权限合适、动作可逆或影响较低、质量经过验证、失败可监测和恢复时，才考虑自动执行。涉及资金、价格承诺、合同、客户外发、数据删除、权限变更或重大业务判断，通常应要求人工审批。

明确停止条件，例如身份或字段缺失、检索结果冲突、超出授权、信心不足、接口异常、重复任务或高风险对象。停下后给出原因、已完成步骤和建议处理人。

## AI 与现有表格、CRM、ERP、飞书或钉钉如何协作？

**标准答案：**

先画出数据和动作流：用户从哪里发起任务、读哪些字段、经什么接口、输出写到哪里、由谁审批、如何记录。检查系统是否有正式 API、测试环境、权限模型、限流和审计能力；没有稳定接口时，评估人工导入或低风险过渡方案，不要默认 UI 自动化就可靠。

尽可能复用企业已有身份和权限控制，明确哪个系统是每类信息的权威来源。给连接器设置超时、重试、幂等和错误提示，并验证字段映射及权限隔离。

## 多 Agent 一定比单 Agent 好吗？

**标准答案：**

不一定。多个 Agent 增加编排、权限、错误传播、成本和调试复杂度。只有当职责可清楚分工、各步骤有独立评估价值、上下游接口明确时才拆分。先做最简单可验证的方案，再根据单一 Agent 或工作流的具体瓶颈扩展。
